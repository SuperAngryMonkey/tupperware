# Tupperware v0.2.4 Release Notes

Follow-up to v0.2.3: the template check and storage-backend probe were still running as serial subprocess calls on every dashboard and `/api/status` request, leaving 2-6s loads on slow hosts. Both now sit behind the same stale-while-revalidate cache and are primed by the startup warm-up.

With this, the request path serves entirely from cache once warm — no subprocess call ever blocks a page load or API response. Measured on the same slow 4-core host: dashboard 36.6s (v0.2.2) -> 2-6s (v0.2.3) -> 0.11s (v0.2.4).

The clone and transfer flows are unaffected: the provisioning scripts validate template, VMID, and storage themselves at execution time, so nothing provisioning-critical relies on cached reads.

## Files changed

- `webui/app.py` — `template_exists()` and `list_storage_backends()` cached (SWR, `TUPPERWARE_CACHE_TTL`), added to startup warm-up
