# Tupperware v0.2.3 Release Notes

**Performance: the dashboard and API are now fast on slow hosts.** Inventory gathering previously shelled out to `pct` twice per running container, serially — on a slow host with 14 containers that meant 30+ second page loads and `/api/containers` responses that outran the MCP client timeout.

## Changes

- **Parallel gathering** — per-container `pct config` / `pct exec` calls now run through a thread pool (up to 8 workers) instead of serially.
- **Stale-while-revalidate cache** — container inventory and host metrics are cached for `TUPPERWARE_CACHE_TTL` seconds (default 30). After expiry the stale copy is served instantly while a background thread refreshes, so responses stay fast at all times after first warm-up.
- **Cache warm-up at startup** — a background thread primes the caches when the service starts.
- **Cache busting** — a completed clone or transfer invalidates the caches so new containers appear immediately.
- **MCP client timeout** — `READ_TIMEOUT` default raised 15s -> 45s and made tunable via `TUPPERWARE_READ_TIMEOUT`, so a cold first call on a slow host survives.

Measured on a slow 4-core host with 14 containers: dashboard 36.6s -> 2.2s, `/api/containers` 30.9s -> 0.1s.

## Notes

- Inventory may be up to `TUPPERWARE_CACHE_TTL` seconds stale; clone/transfer operations bust the cache on completion so their results show up immediately.
- Storage backends and template status are deliberately not cached — provisioning decisions always read them fresh.
- No API shape changes; responses are byte-identical to v0.2.2.

## Files changed

- `webui/app.py` — thread-pool gathering, SWR cache, warm-up, cache busting
- `mcp/tupperware_mcp.py` — configurable `READ_TIMEOUT`, default 45s
